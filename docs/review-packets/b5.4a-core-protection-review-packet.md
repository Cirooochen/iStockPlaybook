# Review Packet — B.5.4A Core Protection with Healthy Thesis

*Self-contained for an external reviewer without repository access.*

---

## 1. What this system is

"Personal Stock Playbook" — a deterministic (non-AI) investment decision engine for a single personal portfolio. Prior validation covered the static baseline, real BUY/SELL propagation, and two concentration thresholds (50% short-term ceiling, 45% target maximum). This packet validates a hard constraint, **HC-003**, which is meant to prevent a tactical SELL from breaching a configured long-term "core" share minimum — and separately checks how it relates to a newer, generic capacity model.

## 2. Relevant prior context

- **HC-003**: a hard, transaction-time rule — if selling would leave fewer shares than the configured core minimum, and the thesis is not deteriorating, the transaction is blocked.
- **Target Position & Sizing Model** (`targetPosition` in engine output): reports capacity tiers, including `maximumNormalTrim` — "how much could be trimmed under normal (thesis-healthy) conditions." Per an earlier design decision (already approved, not revisited here), this figure is bounded by the *stricter* of two floors: the configured core minimum, **or** the share count implied by the strategy's weight-target minimum — whichever is higher.
- For Unity's specific strategy (target weight 40–45%, core 600–650 shares, price €40.46, portfolio total €62,280), the weight-target-implied minimum (616 shares) happens to be **higher** than the core minimum (600 shares) — meaning the weight floor is the stricter constraint here, not the core floor.

## 3. Exact scenario

```
Strategy (unchanged throughout): core range 600-650, target weight 40-45%,
  thesis = INTACT, price = €40.46, portfolioTotal = €62,280 (all held fixed)

Case A: 650 shares, sell 50  -> remaining 600  (exactly at core min)
Case B: 650 shares, sell 51  -> remaining 599  (1 below core min)
Case C: 600 shares, sell 1   -> remaining 599  (1 below core min)
```

## 4. Formula under test

```ts
checkHC003(soldShares, currentShares, coreMin, thesisHealth):
  remaining = currentShares - soldShares
  wouldBreachCore = remaining < coreMin
  thesisDeteriorating = thesisHealth in [WEAKENING, BROKEN]
  triggered = wouldBreachCore && !thesisDeteriorating
```
With thesis INTACT, this reduces to a simple inclusive-floor check: `remaining < coreMin`.

## 5. Actual results (real code run, not hand-calculated)

| | HC-003 triggered | Allowed / Blocked |
|---|---|---|
| A (650 → 600) | false | **Allowed** |
| B (650 → 599) | true | **Blocked** |
| C (600 → 599) | true | **Blocked** |

All three match the stated approved semantics exactly: 600 (the floor itself) is fine, 599 is not.

## 6. The main finding: two layers that don't always agree

At the same starting position (650 shares, thesis INTACT):

| Layer | What it protects | Result |
|---|---|---|
| **HC-003** (hard, transaction-time) | core minimum (600) only | permits selling up to **50** shares |
| **`targetPosition.maximumNormalTrim`** (soft, strategic) | the *stricter* of core minimum (600) or weight-target minimum (616) | permits only **34** shares |

**Case A's sell (50 shares) is legal under HC-003 but exceeds what the strategic capacity model would call "normal" (34).** HC-003 has no awareness of the weight-target floor at all — it only ever checks the core minimum. This is not a bug in either piece: HC-003 behaves exactly as its own narrow specification requires, and `maximumNormalTrim` behaves exactly as its own (already-approved, pre-existing) formula requires. But the two numbers genuinely diverge, and nothing currently signals that divergence to a user beyond the raw figures.

At a different starting position (600 shares), the two layers *do* agree — both report zero further room to sell, because at that point the position is already below the weight floor as well as sitting exactly on the core floor.

## 7. Expected vs. actual

| Expectation | Actual | Match |
|---|---|---|
| A: exactly at floor → allowed | allowed | ✓ |
| B: 1 below floor → blocked | blocked | ✓ |
| C: 1 below floor (different start) → blocked | blocked | ✓ |
| HC-003 and `maximumNormalTrim` "should agree" on the healthy-thesis boundary | **They do not always agree** (34 vs. 50 at 650 shares) — reported, not silently reconciled | Divergence found and documented |

## 8. Test results

New test (5 tests) calls the real `checkHC003()` for all three cases and computes `targetPosition.maximumNormalTrim` via the real `runDecisionEngine()` at both starting positions, asserting the divergence explicitly at 650 shares and the agreement at 600 shares. Full suite: 82/82 passing. Type check, lint, build all clean.

## 9. Bug vs. rule/model-design distinction

No implementation bugs. One **new** rule/model design question surfaced (not previously tracked): should HC-003 ever consider the weight-target floor, not just the core floor? Not resolved here.

## 10. Relevant code (excerpted)

```ts
// hard-constraints.ts — core-only, by design
export function checkHC003(soldShares, currentShares, coreMin, thesisHealth) {
  const wouldBreachCore = (currentShares - soldShares) < coreMin;
  ...
}

// target-position.ts — core-AND-weight-aware, by earlier design decision
maximumNormalTrim = max(0, currentShares - feasibleStrategyRange.min)
// feasibleStrategyRange.min = max(weightShareRange.min, coreShareRange.min)
```

## 11. Assumptions / uncertainties

- This packet only tests thesis = INTACT. HC-003's `thesisDeteriorating` carve-out (WEAKENING/BROKEN disables core protection entirely) is untested here — reserved for B.5.4B.
- The divergence in §6 is specific to Unity's current numbers, where the weight floor (616) happens to exceed the core floor (600). A strategy where the core floor is higher would see the opposite relationship (HC-003 the *more* restrictive layer).

## 12. Open questions for the reviewer

1. Is HC-003's core-only scope intentional and should stay that way, or should it eventually be widened to also consider the weight-target floor that `maximumNormalTrim` already accounts for?
2. Should a user be shown *any* signal (not necessarily a block) when a legal, HC-003-clean transaction would exceed the strategic `maximumNormalTrim` guidance?
3. Does this interact with the already-open "transaction recording vs. Playbook recommendation" question from B.5.2B, or should the two stay independent?
