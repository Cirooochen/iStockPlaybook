# Review Packet — B.5.3B 45% Target Boundary Validation

*Self-contained for an external reviewer without repository access.*

---

## 1. What this system is

"Personal Stock Playbook" — a deterministic (non-AI) investment decision engine for a single personal portfolio. Prior validation (B.5.1–B.5.3A) confirmed the static baseline, real BUY/SELL propagation, and the 50% short-term accumulation-ceiling threshold. This packet tests a second, different threshold: the **45% medium-term target maximum** — the boundary between "still overweight" and "on target."

## 2. Relevant prior context

- **B.5.3A** established that the 50% short-term ceiling and the 40–45% medium-term target range are two different thresholds answering two different questions — clearing one doesn't mean satisfying the other.
- **`ConcentrationState`** (older, finer-grained: WITHIN_TARGET / MODERATELY_OVERWEIGHT / OVERWEIGHT / SEVERELY_OVERWEIGHT) drives stance.
- **`PositionSizingState`** (newer, coarser: UNDERWEIGHT / WITHIN_TARGET / OVERWEIGHT) drives capacity direction, from the approved Target Position & Sizing Model.
- **Feasible Strategy Range**: the intersection of the weight-implied share range and the (optional) core share range — for Unity, the core ceiling (650 shares) is *tighter* than the weight ceiling (692 shares), so it binds first.
- A known, already-documented gap: current code maps `MODERATELY_OVERWEIGHT` to stance `HOLD`; the project's spec groups it with `OVERWEIGHT` under `HOLD_TRIM`. Reconfirmed (not fixed) whenever a scenario lands in that tier.

## 3. Exact scenario inputs

```
Fixed across all three:
  portfolioTotal = €62,280, price = €40.46
  strategy: targetWeightRange = 40–45%, shortTermCeiling = 50%, coreRange = 600–650
  thesis = INTACT, scorecard = unchanged
  position.shares = 692 (= weightShareRange.max), avgCost = €27.76 (both fixed)

Varied:
  position.portfolioWeightPct = 45.1  |  45.0  |  44.9
```

Shares are pinned at exactly `weightShareRange.max` (692) so the share-driven capacity fields isolate purely to the weight-threshold question — this is a deliberate methodological choice (same pattern as the B.5.3A packet), not a claim about a real transaction producing these numbers.

## 4. Formulas / rules involved

```
PositionSizingState: WITHIN_TARGET if 40 <= weight <= 45 (inclusive both ends)
ConcentrationState:  WITHIN_TARGET if weight <= 45 (same inclusive upper bound)

ADD zone: WITHIN_TARGET + accumulation-enabled -> ACTIVE
          MODERATELY_OVERWEIGHT + accumulation-enabled -> WATCH

Feasible Strategy Range = intersect([616,692], [600,650]) = [616,650]
  (the core ceiling, 650, binds tighter than the weight ceiling, 692)

trimCapacity.minimum       = max(0, shares - 692)   // weight-only
trimCapacity.preferred      = max(0, shares - clamp(shares,616,650))  // core-aware
trimCapacity.maximumNormal = max(0, shares - 616)                    // core-aware
```

## 6. Expected vs. actual

All stated expectations matched: 45.1% stays OVERWEIGHT relative to target; 45.0% and 44.9% are both WITHIN_TARGET (45% confirmed as an inclusive upper bound for both classification models); HC-001 was already cleared at all three (well below the unrelated 50% ceiling); crossing the boundary produces a real ADD-zone transition (WATCH → ACTIVE).

## 7. The key nuance this test was designed to surface

**Stance stayed `HOLD` across all three weights — for two structurally different reasons, not one.** At 45.1% it's the `MODERATELY_OVERWEIGHT` branch (the known design gap — see §2). At 45.0%/44.9% it's the *separate*, intentional `WITHIN_TARGET` fallback (explicitly commented in the code as a Phase-C placeholder). These look identical in the output but are not the same finding.

**Trim capacity did not drop to zero at WITHIN_TARGET.** With shares pinned at the weight ceiling (692), `trimCapacity.minimum` is 0 throughout (no *mandatory* trim once weight-compliant) — but `preferred` (42) and `maximumNormal` (76) stayed non-zero even at 45.0%/44.9%, because the **core range (600–650) is tighter than the weight range (up to 692)** for this configuration. A position can satisfy the weight target and still show real "headroom" toward the core. This is intentional, documented model behavior (only the Minimum tier is weight-only; Preferred/MaximumNormal are core-aware), not a defect — but it means "WITHIN_TARGET" must not be read as "capacity is zero everywhere."

## 8. Test results

New test file (6 tests) constructs the three `EngineInput`s directly, asserts the inclusive-boundary transition, the already-cleared HC-001, the ADD zone transition, the non-zero-capacity nuance, and reconfirms the MODERATELY_OVERWEIGHT design question without fixing it. Full suite: 77/77 passing. Type check, lint, build all clean.

## 9. Relevant code paths (excerpted)

`concentration.ts` / `target-position.ts` — the shared inclusive boundary:
```ts
if (weightPct <= targetMaxPct) return "WITHIN_TARGET";           // concentration.ts
...
WITHIN_TARGET if targetWeightMinPct <= currentWeightPct <= targetWeightMaxPct  // target-position.ts
```

`action-zones.ts` — the meaningful transition:
```ts
if (concentrationState === "WITHIN_TARGET") return "ACTIVE";
if (concentrationState === "MODERATELY_OVERWEIGHT") return "WATCH";
```

## 10. Bug vs. model-design distinction

No new implementation bugs. One pre-existing design question (MODERATELY_OVERWEIGHT → HOLD vs. spec's HOLD_TRIM) reconfirmed, only at the 45.1% end — not newly discovered, not resolved.

## 11. Assumptions / uncertainties

- Shares pinned at exactly `weightShareRange.max` (692) is a deliberate isolation choice, chosen to make the capacity numbers land on a clean, illustrative boundary value — not a claim that a real position would sit exactly there.
- The core-range-tighter-than-weight-range relationship observed here is specific to Unity's current configuration (core max 650 < weight-implied max 692); it would not generalize to a strategy where the core range is wider than the weight range.

## 12. Open questions for the reviewer

2. Does the "same output value (`HOLD`), two different causes" situation (§7) suggest the stance layer should eventually distinguish *why* it returned HOLD, for clearer downstream explanation?
3. Anything about the boundary-inclusivity choice (45.0% treated as fully on-target) that looks like it deserves a second look?
