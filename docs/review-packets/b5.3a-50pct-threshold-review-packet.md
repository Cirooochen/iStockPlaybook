# Review Packet — B.5.3A 50% Concentration Threshold Validation

*Self-contained for an external reviewer without repository access.*

---

## 1. What this system is

"Personal Stock Playbook" — a deterministic (non-AI) investment decision engine for a single personal portfolio. Prior validation (B.5.1, B.5.2) confirmed the engine's static baseline and real BUY/SELL transaction propagation. This packet is a narrower, targeted test: the exact numeric behavior right around one specific hard-constraint threshold — the 50% "short-term accumulation ceiling" — independent of any transaction.

## 2. Relevant prior context

- **HC-001**: if portfolio weight exceeds a configured "short-term max weight," accumulation (ADD) is disabled.
- Separately, the strategy also defines a **40–45% "medium-term target range"** — a different, tighter threshold describing where the position is considered "correctly sized" long-term.
- The whole point of this test: **these are two different thresholds answering two different questions.** Clearing the 50% ceiling doesn't mean the position is anywhere near the 40–45% target.
- A newer, generic **Target Position & Sizing Model** (`targetPosition` in engine output) classifies a position as UNDERWEIGHT/WITHIN_TARGET/OVERWEIGHT strictly relative to the 40–45% range — a separate classification from the older 4-tier `ConcentrationState` (which is itself relative to the same 40–45% range, but with finer overweight-severity gradations, and is what stance derivation uses).
- A previously-known, already-documented gap: the current stance logic maps `MODERATELY_OVERWEIGHT` to plain `HOLD`, while the project's own spec groups `MODERATELY_OVERWEIGHT` and `OVERWEIGHT` together under `HOLD_TRIM`. Not fixed yet; flagged again here if it resurfaces.

## 3. Exact scenario construction

Three inputs, one variable changed at a time:

```
Fixed across all three:
  portfolioTotal = €62,280, price = €40.46
  strategy: targetWeightRange = 40–45%, shortTermCeiling = 50%, coreRange = 600–650
  thesis = INTACT, scorecard = unchanged (fundamentals/valuation/momentum untouched)
  position.shares = 770, avgCost = €27.76 (both fixed)

Varied:
  position.portfolioWeightPct = 50.1  |  50.0  |  49.9
```

The weight field is set directly rather than derived from an integer share count, because the hard-constraint check reads it directly, and no integer number of shares at this price/total lands on exactly 50.00% — setting it directly is the only way to test the exact boundary precisely, not approximately.

## 4. Formulas / rules involved

```
HC-001: triggered = weightPct > 50           (strict greater-than)

ConcentrationState: ratio = weight / 45
  moderate boundary = 45 × 1.15 = 51.75
  severe boundary    = 45 × 1.30 = 58.5
  49.9–50.1% all fall in (45, 51.75] -> MODERATELY_OVERWEIGHT for all three

Stance (current code): MODERATELY_OVERWEIGHT -> "HOLD"
Stance (per project spec): MODERATELY_OVERWEIGHT/OVERWEIGHT -> "HOLD_TRIM" (grouped)

ADD action zone:
  !accumulationEnabled           -> INACTIVE
  accumulationEnabled + WITHIN_TARGET       -> ACTIVE
  accumulationEnabled + MODERATELY_OVERWEIGHT -> WATCH
```

## 5. Actual results (real code run, not hand-calculated)

| | 50.1% | 50.0% | 49.9% |
|---|---|---|---|
| `concentration.state` | MODERATELY_OVERWEIGHT | MODERATELY_OVERWEIGHT | MODERATELY_OVERWEIGHT |
| `targetPosition.positionSizingState` | OVERWEIGHT | OVERWEIGHT | OVERWEIGHT |
| `HC-001 triggered` | **true** | **false** | **false** |
| `accumulationEnabled` | false | true | true |
| `stance` | HOLD | HOLD | HOLD |
| `ADD zone` | INACTIVE | **WATCH** | **WATCH** |
| `TRIM_1` / `TRIM_2` | INACTIVE / INACTIVE | INACTIVE / INACTIVE | INACTIVE / INACTIVE |

Note: `50.0%` clears HC-001 because the check is strictly `>`, not `>=` — the boundary value itself is already in the "cleared" state, not the "triggered" one.

## 6. Expected vs. actual

Every expectation matched: crossing to ≤50% clears HC-001; ADD flips from INACTIVE to WATCH (not ACTIVE — the position still isn't near the 40–45% range); `positionSizingState` stays OVERWEIGHT at 49.9% even though the hard constraint has cleared. **This last point is the entire purpose of this test, and it held**: passing one threshold (accumulation ceiling) is confirmed independent of, and insufficient for, satisfying the other (target range).

## 7. Rule/model design question (not new — reconfirmed)

All three scenarios land in `MODERATELY_OVERWEIGHT`, which resurfaces the already-known stance gap described in §2: current code returns `HOLD`, the spec's own text would suggest `HOLD_TRIM`. This is **not fixed here** — it was anticipated as a possible outcome of this specific test and is reported, not resolved, per instruction.

## 8. Test results

New test file (4 tests) constructs the three `EngineInput`s directly (per instruction — this is threshold/state validation, not transaction accounting, so a real BUY/SELL wasn't required or used) and asserts the boundary semantics via the real `runDecisionEngine()`. Full suite: 71/71 passing. Type check, lint, build all clean.

## 9. Relevant code paths (excerpted)

`hard-constraints.ts` — the exact boundary under test:
```ts
export function checkHC001(weightPct: number, accumulationMaxWeightPct: number): HardConstraintResult {
  const triggered = weightPct > accumulationMaxWeightPct;  // strict >, boundary value clears
  ...
}
```

`action-zones.ts` — why ADD goes to WATCH, not ACTIVE, once cleared:
```ts
case "ADD":
  if (!accumulationEnabled) return "INACTIVE";
  if (concentrationState === "WITHIN_TARGET") return "ACTIVE";
  if (concentrationState === "MODERATELY_OVERWEIGHT") return "WATCH";
  return "INACTIVE";
```

## 10. Bug vs. model-design distinction

No implementation bugs found. One pre-existing design question (§7) reconfirmed, not newly discovered and not resolved.

## 11. Assumptions / uncertainties

- `position.shares` (770) and `averageCostEur` (€27.76) were held fixed across all three scenarios purely as realistic-looking placeholders; they don't need to precisely reverse-engineer the target weight, since the hard-constraint/concentration logic reads `portfolioWeightPct` directly rather than recomputing it from shares × price / total. This is a deliberate simplification for isolating the threshold variable, not a claim about how a real transaction would produce these exact numbers.
- The 45% target-range boundary (a related but distinct threshold) is explicitly out of scope for this packet — reserved for B.5.3B.
