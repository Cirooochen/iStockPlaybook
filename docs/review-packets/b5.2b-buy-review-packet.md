# Review Packet — B.5.2B BUY Transaction Validation

*Self-contained for an external reviewer without repository access.*

---

## 1. What this system is

"Personal Stock Playbook" — a deterministic (non-AI) investment decision engine for a single personal portfolio. A prior validation pass (B.5.2A) confirmed a real SELL transaction propagates correctly end-to-end, including a fix that keeps the tracked portfolio total flat when shares are sold (proceeds become cash, not deleted value). This packet is the mirror-image test: **does a real BUY transaction propagate correctly**, and does it expose anything new about how the system's hard-constraint rules interact with transaction entry.

## 2. Relevant prior context

- **Portfolio Total = Securities + Cash** (fixed before this test): a BUY converts existing cash into stock — the total should stay flat, not grow (a prior version treated every BUY as externally-funded new capital, growing the total; this was deliberately changed so BUY and SELL share the same convention).
- **Target Position & Sizing Model** (`targetPosition` in engine output): a generic model reporting a position's UNDERWEIGHT/WITHIN_TARGET/OVERWEIGHT classification and three capacity tiers (minimum/preferred/maximumNormal) for trimming or adding — capacity, not a recommendation.
- **HC-001**: a hard constraint — if portfolio weight exceeds a "short-term ceiling" (50% here), accumulation (ADD) is disabled.

## 3. Exact scenario

```
Pre-transaction (Unity baseline):
  shares = 902, avgCost = €27.76, price = €40.46
  portfolioTotal = €62,280
  strategy: targetWeightRange = 40–45%, shortTermCeiling = 50%, coreRange = 600–650 shares
  thesis = INTACT
  (already above the 50% ceiling pre-transaction: 58.6%)

Transaction: BUY 50 shares @ €40.46 (market price, funded from existing portfolio cash)

Held constant: price, thesis, fundamentals, valuation, momentum.
```

## 4. Formulas / rules involved

```
applyBuy (weighted-average accounting):
  newShares = oldShares + boughtShares
  newAvgCost = (oldShares×oldAvgCost + boughtShares×buyPrice) / newShares
  newValue = newShares × price
  (no realized gain on a BUY — only SELL realizes gains/losses)

Portfolio total (cash-inclusive convention):
  newPortfolioTotal = oldPortfolioTotal   (BUY draws from existing cash, doesn't inject new capital)

Concentration state:
  ratio = weight / targetMax; severe-overweight boundary at ratio 1.30

HC-001: weight > shortTermCeiling (50%) -> accumulation disabled
HC-003: SELL-only (core-breach protection) — structurally not applicable to a BUY

Target Position capacity tiers (unchanged model, see B.5.2A packet for full formulas):
  trimCapacity = { minimum, preferred, maximumNormal } — all increase when shares increase
```

| Average cost | €27.76 | **€28.43** (rose — see note below) |
| Position value | €36,494.92 | €38,517.92 |
| Unrealized return | 45.75% | **42.33%** (fell — see note below) |
| Portfolio total | €62,280 | **€62,280 (unchanged)** |
| Portfolio weight | 58.6% | **61.85%** |
| `concentration.state` | SEVERELY_OVERWEIGHT | SEVERELY_OVERWEIGHT (no tier change — ratio worsens within the same tier) |
| `concentration.tacticalInventory.aboveCoreMax` | 252 | 302 |
| `concentration.trimSizing.maxTacticalTrim` | 252 | 302 |
| `targetPosition.trimCapacity` | {210, 252, 286} | **{260, 302, 336}** |
| `constraints.hc001.triggered` | true | true (unchanged — already over the ceiling before this BUY) |
| `constraints.accumulationEnabled` | false | false |

| `actionZones.TRIM_1` / `TRIM_2` | ACTIVE / WATCH | ACTIVE / WATCH (unchanged) |

**Average-cost/unrealized-return note:** the buy price (€40.46) is above the pre-existing average cost (€27.76). Blending new shares in at a price above the current average pulls the weighted average up, which — measured against that new, higher average — makes the % unrealized gain look smaller, even though the market price didn't move and the original shares' euro gain is untouched. This is standard weighted-average accounting (not tax-lot), and is expected, not a defect.

## 6. Expected vs. actual

Every stated expectation (shares increase, total preserved, weight increases, concentration worsens-or-preserves-severe, tactical inventory and all capacity tiers increase, thesis unchanged, HC-001 stays triggered, ADD stays disabled, trim urgency preserved/increased) **matched exactly**. Stance and action zones were *not* pre-assumed to change — they didn't, because no severity-tier boundary was crossed (contrast with B.5.2A's SELL, which did cross one).

## 7. The central finding: accounting vs. rules-layer, and a UI gap

Two distinct questions, kept separate per instruction:

- **A. Can the engine mathematically process this BUY?** Yes — cleanly, no errors, correct weighted-average math.
- **B. Does the strategy/rules layer say this BUY should be permitted?** No — `HC-001` (accumulation disabled) was already true *before* this transaction and stays true after.

**What we found:** `AddTransactionModal`'s Confirm button has no check against HC-001/`accumulationEnabled` for a BUY at all — its gating logic is just `price > 0 && shares > 0 && !oversell`, full stop. (Compare: a SELL that would breach the core minimum *is* blocked, via a separate hard-constraint check, HC-003.) So today, a user can freely record a BUY that the Playbook's own rules say shouldn't happen, and the engine will dutifully compute a worse position for it.

**This is reported as a RULE / PRODUCT DESIGN QUESTION, not an implementation bug**, because there's a legitimate argument either way: the app may need to accurately *record* a real-world transaction that already happened, even one the Playbook wouldn't have recommended — versus the argument that a safety rail (mirroring the existing SELL-side HC-003 gate) would prevent accidental over-accumulation. **No blocking behavior was changed** in this validation pass.

`accounting.ts` — the convention under test:

```ts
export function calcPortfolioTotalAfterBuy(oldTotalPortfolioEur: number): number {
  return oldTotalPortfolioEur; // funded from existing cash, total unchanged

```

`AddTransactionModal.tsx` — the gap described in §7:
```ts
const isValid = price > 0 && shares > 0 && !oversell;   // no HC-001 check here
const hc003 =
  type === "SELL" && shares > 0 && !oversell && strategy.coreSharesMin !== undefined
    ? checkHC003(shares, position.shares, strategy.coreSharesMin, thesisHealth)
    : null;                                              // HC-003 is SELL-only, by design
const canConfirm = isValid && !hc003?.triggered;          // BUY has nothing analogous
```

## 10. Assumptions / uncertainties

- The buy price equals the "current market price" exactly (no slippage modeled) — same assumption as B.5.2A's SELL scenario, for consistency.
- `targetPosition.positionSizingState` stayed "OVERWEIGHT" through this transaction, same as B.5.2A — this model has no severity granularity, by design, not a defect.

## 11. Bug vs. rule/product-design distinction

No implementation bugs found. Two items surfaced, both classified as design questions rather than bugs:
1. **New this stage:** should BUY be gated by HC-001 at entry time? (§7)
2. **Standing, not new:** `concentration.trimSizing` vs. `targetPosition.trimCapacity` still numerically coincide (302 = 302) for Unity's specific configuration — already tracked in the B.5.1 Resolution closeout, reconfirmed here with larger numbers, not reclassified.

## 12. Open questions for the reviewer

1. Should HC-001 block BUY entry (mirroring HC-003's SELL-side block), or is unrestricted recording intentional so the app can log transactions that happened in reality even against the Playbook's advice?
2. Would a non-blocking *warning* (visible but not preventing confirmation) be a reasonable middle ground worth prototyping later?
3. Anything in the concentration/stance/action-zone "no tier crossing" behavior that looks suspicious to a fresh reviewer, independent of what's reported here?
