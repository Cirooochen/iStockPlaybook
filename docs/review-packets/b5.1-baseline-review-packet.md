*Self-contained for an external reviewer without repository access. Do not assume any other context.*

## 1. What this system is

"Personal Stock Playbook" — a deterministic (non-AI) investment decision engine for a single personal portfolio. Given a position's current numbers and a written strategy (target weight ranges, core share counts), a pure-function "Decision Engine" computes: concentration risk state, hard-constraint checks, an investment stance (e.g. HOLD, TRIM, ADD), action-zone eligibility, a scorecard, and tactical trim sizing. No AI or live market data is involved yet — this is Phase B.5 ("Algorithm Validation"), which exists specifically to check the deterministic math/rules before real data or AI are wired in.

## 2. Architecture (minimal)

A single composition function, `runDecisionEngine(input: EngineInput): EngineOutput`, sequences several pure sub-functions:

```
thesis (pass-through) → signals (pass-through) → concentration classification
  → hard constraints (HC-001, HC-002) → stance → action zones → scorecard → trim sizing
```

`EngineOutput` shape:

```ts
interface EngineOutput {
  concentration: {
    state: "WITHIN_TARGET" | "MODERATELY_OVERWEIGHT" | "OVERWEIGHT" | "SEVERELY_OVERWEIGHT";
    targetShares: number;
    sharesToTarget: number;
    tacticalInventory: { aboveCoreMax: number; maxSellToCore: number };
    trimSizing: { level1: number; level2: number; level3: number; maxTacticalTrim: number };
  };
  thesis: { health: "STRENGTHENING" | "INTACT" | "MIXED" | "WEAKENING" | "BROKEN" };
  constraints: {
    hc001: { code: string; triggered: boolean; description: string };
    hc002: { code: string; triggered: boolean; description: string };
    fired: Array<{ code: string; triggered: boolean; description: string }>;
    accumulationEnabled: boolean;
  };
  stance: string; // e.g. "HOLD_GRADUALLY_TRIM"
  actionZones: Array<{ type: string; state: "ACTIVE" | "INACTIVE" | "WATCH" | "CONDITIONAL"; ... }>;
  scorecard: { fundamentals, valuation, momentum, thesisHealth, positionFit, concentrationRisk: { score: number; state: string } };
}
```

## 4. Formulas / rules actually used

```
concentration ratio = weight / targetMax = 58.6 / 45 = 1.302
  WITHIN_TARGET:            weight <= targetMax
  MODERATELY_OVERWEIGHT:    targetMax < weight <= targetMax × 1.15
  OVERWEIGHT:                targetMax × 1.15 < weight <= targetMax × 1.30
  SEVERELY_OVERWEIGHT:       weight > targetMax × 1.30
  → 45 × 1.30 = 58.5; 58.6 > 58.5 → SEVERELY_OVERWEIGHT

HC-001: weight > shortTermMaxWeightPct → accumulation disabled
  → 58.6 > 50 → triggered

stance priority matrix (simplified, only the branches implemented today):
  thesis BROKEN → THESIS_REVIEW
  thesis WEAKENING + (OVERWEIGHT|SEVERELY_OVERWEIGHT) → REDUCE_RISK
  SEVERELY_OVERWEIGHT → HOLD_GRADUALLY_TRIM
  OVERWEIGHT → HOLD_TRIM
  MODERATELY_OVERWEIGHT → HOLD
  else → HOLD

positionFit score = 100 − 200 × ((weight − targetMax) / targetMax), scaled /10, floor 1
  → 100 − 200×(13.6/45) = 100 − 60.44 = 39.56 → round(3.956) → 4/10, "Neutral" (≥4)

targetShares = floor(portfolioTotal × targetMax% / price) = floor(62280 × 0.45 / 40.46) = floor(692.68) = 692
sharesToTarget = shares − targetShares = 902 − 692 = 210
aboveCoreMax = max(0, shares − coreMax) = 902 − 650 = 252

trim sizing (AS SPECIFIED in the project's own spec doc, §21):
  max_tactical_trim = min(sharesToTarget, aboveCoreMax) = min(210, 252) = 210
  level1 = round(max_tactical_trim × 0.30)
  level2 = round(max_tactical_trim × 0.35)
  level3 = remainder

trim sizing (AS ACTUALLY IMPLEMENTED — see finding below):
  max_tactical_trim = aboveCoreMax = 252   ← min() step with sharesToTarget is MISSING
  level1 = round(252 × 0.30) = 76
  level2 = round(252 × 0.35) = 88
  level3 = 252 − 76 − 88 = 88
```

## 9. Relevant code paths (excerpted, not full files)

`concentration.ts` — the trim-sizing function itself is correct, generic, and unaware of `sharesToTarget`:

```ts
export function calcTrimSizing(maxTacticalTrim: number): TrimSizing {
  const { level1Fraction, level2Fraction } = RULESET.trimStaging; // 0.30, 0.35
  const level1 = Math.round(maxTacticalTrim * level1Fraction);
  const level2 = Math.round(maxTacticalTrim * level2Fraction);
  const level3 = Math.max(0, maxTacticalTrim - level1 - level2);
  return { level1, level2, level3, maxTacticalTrim };
}
```

`engine.ts` — the call site, where the bug actually lives (passes `aboveCoreMax` alone, never combines with `sharesToTarget`):

```ts
const tacticalInventory = calcTacticalInventory(position.shares, strategy.coreSharesMax, strategy.coreSharesMin);
const trimSizing = calcTrimSizing(tacticalInventory.aboveCoreMax); // ← should be Math.min(sharesToTarget, tacticalInventory.aboveCoreMax)
```

The project's own spec document (§21) defines:
```
shares_to_target   = current_shares - target_shares
available_tactical = max(0, current_shares - core_max)
max_tactical_trim   = min(shares_to_target, available_tactical)
```

## 10. Finding — for review

**Finding 1 — Trim sizing does not cap at the shares actually needed to reach target.**
- **Classification:** Implementation bug (not a rule-design ambiguity — the spec's formula is unambiguous and the code cites it in a comment but doesn't fully implement it).
- **Magnitude:** In this scenario, the engine stages 252 tactical shares (20% more than the 210 actually needed to reach the 45% target weight). If a user acted on the L1/L2/L3 suggestions at face value, they could sell more than the target strategy calls for.
- **Not fixed** in this validation pass, per project instruction (validation must not silently trigger a rule/code change).
- **Question for reviewer:** Is `min(sharesToTarget, availableTactical)` unambiguously the intended behavior (i.e., should this simply be fixed), or is there a plausible reading of the product intent where trimming the *entire* above-core tactical block (252) — rather than just enough to hit target (210) — is deliberate (e.g., "core protection" as the only ceiling, target-weight as advisory only)? The current code has no comment indicating an intentional deviation, which weakly favors "bug," but this is a product/strategy judgment call, not a pure math question.

## 11. Assumptions / uncertainties

- Position data (902 shares, €27.76 avg cost, etc.) is hand-authored seed data representing "the current real position," not the output of a replayed transaction history. It was checked for internal arithmetic consistency (price × shares = value, etc.) and passes, but its ultimate provenance (i.e., that 902/€27.76 are the *true* real-world numbers) is asserted, not independently verifiable from this repo alone.
- "Company state" and "Valuation state" bucket classifications described in the project's spec (§17) do not exist in the implementation at all yet — the stance logic is a simplified subset of the spec's full matrix. This doesn't affect this specific scenario (the branch it hits is implemented and correct) but means later scenarios (within-target, mixed thesis) may hit unimplemented branches.
- Fundamentals/valuation/momentum scores are static placeholder data, not live computation — by design at this project phase, not a defect.
