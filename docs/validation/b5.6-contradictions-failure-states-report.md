## Findings

1. **PASS — contradictions remain visible, not blended (Scenario 1).**
   `EngineOutput.scorecard` keeps fundamentals/valuation/momentum/
   thesisHealth/positionFit/concentrationRisk as six independent fields.
   No "overall"/"composite" score exists anywhere in `EngineOutput`
   that would average a 9 fundamentals score against a 2 valuation
   score into one number. The spec §25 requirement ("do not hide
   disagreement by averaging everything into one number") holds for the
   current architecture.

2. **PASS, with a carried-forward gap — valuation/fundamentals don't
   yet feed the rule layer (Scenario 1).** Expensive valuation (score
   2) is visible in the scorecard but does not additionally suppress
   ADD or alter stance — `deriveStance` and `deriveActionZoneState`
   don't read `scorecard.valuation`/`fundamentals` at all yet. ADD is
   already `INACTIVE` here via concentration (OVERWEIGHT) and HC-001,
   so this scenario doesn't surface a new gap — it's the same,
   already-documented Phase C deferral (spec §22's
   `fundamental_score >= 60`/`valuation_score >= 60` clauses) reconfirmed
   under a genuinely contradictory input, not a new finding.

3. **PASS — thesis correctly overrides strong company signals for ADD
   eligibility (Scenario 2).** With fundamentals/valuation/momentum all
   at 9/10 and accumulation enabled (HC-001/002 both clear), ADD is
   still `INACTIVE` solely because of the spec §22 thesis-eligibility
   gate implemented in B.5.5 (MIXED is thesis-ineligible). The
   contradiction is preserved rather than hidden: the strong scores
   stay visible in the scorecard, while the action layer independently
   declines to recommend ADD. This is exactly the "Company CONSTRUCTIVE
   / Stance HOLD" pattern spec §25 describes as the desired behavior,
   confirmed working end-to-end for the ADD-eligibility gate
   specifically.

4. **NOT YET IMPLEMENTED — missing required signal data (Scenario 3).**
   The domain layer has no representation of "value absent" anywhere:
   - `ScoreItem`/`Scorecard`/`MarketData`/`Position` have no optional
     (`field?:`) or nullable (`| null`/`| undefined`) fields — a caller
     cannot express "this dimension has no data" at the type level, only
     supply some concrete score.
   - There is no `INCOMPLETE` value in `Stance`, `ActionZoneState`, or
     `Confidence` — spec §16's HC-005 (`missing evidence ⇒ Playbook =
     INCOMPLETE`) has no destination state to transition to even if it
     were implemented.
   - `hard-constraints.ts` exports only `checkHC001`/`002`/`003`; HC-004
     and HC-005 do not exist.
   - Consequence, demonstrated directly: a scorecard where every
     dimension is `{ score: 0, state: "Weak" }` (the closest available
     stand-in for "no data") is processed identically to a genuinely
     unhealthy-but-known position — `runDecisionEngine` still returns a
     complete, ordinary `HOLD` stance and `ADD = ACTIVE`, with nothing
     in the output distinguishing "we know this is bad" from "we don't
     know." This directly answers the review question: **yes, in the
     current architecture, missing data can still produce a fully
     assertive action output**, because the architecture has no
     mechanism to detect or represent that data is missing in the first
     place.

5. **NOT YET IMPLEMENTED — stale market/fundamental data (Scenario 4).**
   `EngineInput` does not carry `MarketData.updatedAt` (or any
   timestamp) at all — only a bare `executionPriceEur: number` crosses
   the boundary into the engine. This is stronger than "the rule isn't
   coded": the input the rule would need doesn't reach the engine at
   all. Separately, `Playbook.confidence` is a static seed field with no
   `deriveConfidence` function anywhere in the domain layer;
   `RULESET.confidence.mediumThreshold`/`highThreshold` (spec §24's
   weights) are configured but unread. `EngineOutput` itself has no
   `confidence` field, so spec §16's HC-004 (`stale data ⇒ prohibit
   HIGH-confidence output`) has no confidence value in the engine's
   output to prohibit even in principle. Same answer as Scenario 3:
   staleness cannot currently suppress or downgrade anything, because
   the architecture has no path for it to reach the decision layer.

No implementation bugs in any scenario — items 4 and 5 are architecture
absence, not incorrect behavior of existing code, consistent with the
roadmap's own expectation for this checkpoint ("expect this stage to
surface mostly NOT YET IMPLEMENTED findings").
