# B.5.3A — 50% Concentration Threshold Validation Report

**Status:** COMPLETE
**Date:** 2026-09-08
**Scope:** the short-term 50% accumulation ceiling (HC-001) only. The 45% medium-term target boundary is explicitly **not** tested here (B.5.3B). B.5.3B and later stages not started.
**Method:** three `EngineInput` objects constructed directly (threshold/state validation, not transaction accounting, per instruction) with a single independent variable (`position.portfolioWeightPct`); fed through the real `runDecisionEngine()`.
**Rule:** no discrepancies fixed automatically.

---

## 1. Exact scenario construction

All three scenarios share identical `portfolioTotalEur` (€62,280), `executionPriceEur` (€40.46), `strategy` (target 40–45%, short-term ceiling 50%, core 600–650), `thesisHealth` (INTACT), and `scorecard` (Unity's static values, fundamentals/valuation/momentum untouched). Only `position.portfolioWeightPct` varies:

```ts
position = {
  shares: 770,
  averageCostEur: 27.76,
  valueEur: 770 × 40.46,                    // held fixed
  unrealizedReturnPct: (40.46−27.76)/27.76,  // held fixed
  portfolioWeightPct: <50.1 | 50.0 | 49.9>,  // the only independent variable
}
```

`portfolioWeightPct` is set directly rather than derived by reverse-engineering a share count, because `checkHC001`/`classifyConcentration` read this field directly (not recomputed from shares×price/total) — this isolates the threshold variable precisely, including the exact-50.0% case, which an integer share count could not hit exactly (770 shares × €40.46 / €62,280 ≈ 49.98%, not exactly 50.00%).

## 2. Threshold formulas

```
HC-001 (hard-constraints.ts):
  triggered = weightPct > accumulationMaxWeightPct   // STRICT greater-than
            = weightPct > 50

ConcentrationState (concentration.ts):
  ratio = weight / 45
  moderate boundary = 45 × 1.15 = 51.75
  severe boundary   = 45 × 1.30 = 58.5
  All three test weights (49.9–50.1) fall between 45 and 51.75 -> MODERATELY_OVERWEIGHT

Stance (stance-rules.ts):
  MODERATELY_OVERWEIGHT -> "HOLD" (current code)
  Spec §18: "MODERATELY_OVERWEIGHT/OVERWEIGHT -> HOLD_TRIM" (groups them together)

ADD action zone (action-zones.ts):
  !accumulationEnabled -> INACTIVE
  accumulationEnabled && WITHIN_TARGET -> ACTIVE
  accumulationEnabled && MODERATELY_OVERWEIGHT -> WATCH
```

## 4. Expected vs. actual

| Expectation | Actual | Match |
|---|---|---|
| `weight > 50% → HC-001 triggered` (50.1%) | triggered = true | ✓ |
| `weight <= 50% → HC-001 cleared` (50.0% and 49.9%) | triggered = false for both | ✓ |
| Crossing below 50% clears HC-001 | confirmed at both 50.0% and 49.9% | ✓ |
| Crossing below 50% does NOT mean fully on-target | `positionSizingState` stays OVERWEIGHT at 49.9% (still > 45% target max); ADD goes to WATCH, not ACTIVE | ✓ — this is the central point of B.5.3A, confirmed |

No discrepancy between expected direction and actual result on the core threshold semantics.

## 5. Rule / model design question (anticipated, confirmed)

All three scenarios land in `MODERATELY_OVERWEIGHT`, which the roadmap already flagged as exercising a known, pre-existing gap: `deriveStance`'s `MODERATELY_OVERWEIGHT` branch returns plain `HOLD`, while spec §18 explicitly groups `MODERATELY_OVERWEIGHT/OVERWEIGHT` together under `HOLD_TRIM`. **Confirmed present, not fixed** — classified as **RULE / MODEL DESIGN QUESTION**, consistent with its original classification; not re-litigated or resolved here.
