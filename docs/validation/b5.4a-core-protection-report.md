## 2. HC-003 logic under test

```ts
export function checkHC003(soldShares, currentShares, coreMin, thesisHealth) {
  const remaining = currentShares - soldShares;
  const wouldBreachCore = remaining < coreMin;
  const thesisDeteriorating = thesisHealth === "WEAKENING" || thesisHealth === "BROKEN";
  const triggered = wouldBreachCore && !thesisDeteriorating;
  ...
}
```
With thesis INTACT, `thesisDeteriorating` is always `false`, so `triggered` reduces to `wouldBreachCore` — i.e., `remaining < coreMin` — exactly the scenario this stage targets.

## 5. Relation to `targetPosition.maximumNormalTrim` — different layers, and they do NOT always numerically agree

Computed via the real engine at each starting position (thesis INTACT):

| Starting shares | `positionSizingState` | `feasibleStrategyRange` | `trimCapacity.maximumNormal` | Shares HC-003 alone would permit selling (`shares − coreMin`) |
|---|---|---|---|---|
| 650 | WITHIN_TARGET (42.23% is inside 40–45%) | [616, 650] | **34** | **50** |
| 600 | UNDERWEIGHT (38.98% is below 40%) | [616, 650] | **0** | **0** |

**At 650 shares, the two layers disagree (34 vs. 50), by design.** HC-003 protects only the 600-share core floor. `targetPosition.maximumNormalTrim` is bounded by the *stricter* of two floors — the core minimum (600) **and** the 40%-weight-target-implied minimum (616 shares, per the approved B.5.1 Resolution formula: `maximumNormalTrim = currentShares − feasibleStrategyRange.min`). Because 616 > 600 for Unity's current configuration, the weight floor binds first, making `maximumNormalTrim` (34) more conservative than what HC-003 alone would permit (50). **Case A's sell of 50 shares is HC-003-legal but exceeds what `targetPosition` would call "normal" capacity (34)** — HC-003 does not know about, and does not enforce, the weight-target floor at all.

**At 600 shares, the two layers agree (both say 0 further headroom)** — here the position is already below the weight floor (616) as well as sitting exactly at the core floor (600), so both layers converge on "no more selling."

This is not a bug in either layer — each behaves exactly per its own already-approved specification. It is a genuine, reportable **cross-layer relationship finding**: HC-003 (hard, transaction-time, core-only) and `maximumNormalTrim` (soft, strategic, core-*and*-weight-aware) only coincide when the core floor happens to be the binding constraint, which is not always true for this strategy's configuration.

## 7. New rule/model design question surfaced

**Should HC-003 ever also protect the weight-target floor, or is core-only protection intentional?**

Currently HC-003 is a hard, transaction-blocking rule scoped *only* to the configured core minimum. `targetPosition.maximumNormalTrim` is a softer, strategic guidance number that additionally considers the weight-target floor. A user can execute a real transaction (Case A: sell 50 from 650) that clears HC-003 cleanly but exceeds the strategic model's own "normal" recommendation (34) — HC-003 gives no signal about this at all. Two legitimate positions exist:

- **Core-only is intentional**: HC-003 is meant to be a narrow, hard-and-fast safety rail against breaching the long-term core commitment specifically; the weight-target floor is advisory (strategic capacity), not a transaction-blocking rule, and conflating them would overreach HC-003's stated purpose.
- **Under-protective**: if the weight-target floor is also considered strategically important enough to bound "normal" trimming, a user might reasonably expect *some* signal (even non-blocking) when a transaction would breach it, similar to how HC-003 currently warns/blocks for the core.

**Not resolved here — flagged for product review, not fixed automatically**, per instruction.

## 7a. Resolution (2026-09-09) — RESOLVED: INTENDED CROSS-LAYER DISTINCTION

Product decision, made before starting B.5.4B. This section is additive
— §7 above is preserved as the original finding, not rewritten.

**Decision: keep HC-003 core-only. Do not extend it to the weight-target
floor.** The two layers have deliberately different responsibilities:

- **HC-003** — protects only the explicitly configured core-share
  minimum. Answers *"Would this SELL breach the committed long-term
  core?"* Formula unchanged: `remainingShares < coreSharesMin`, subject
  to the existing thesis-health carve-out.
- **`maximumNormalTrim`** — protects the upper boundary of *normal*
  strategic trimming, bounded by `max(coreSharesMin, weightShareRange.min)`.
  May be more conservative than HC-003 whenever the weight floor is
  stricter than the core floor, as it is for Unity's current
  configuration.

The Unity 650-share example is now read as an intentional **three-level
distinction**, not an open question:

```text
SELL 34      → within normal strategic capacity
SELL 35-50   → exceeds normal strategic capacity, still HC-003-clean
SELL 51+     → breaches the core floor, HC-003 triggers
```

No application code, formula, or test was changed by this resolution —
it is a semantic/model clarification only. Full responsibility-boundary
documentation added to `docs/playbook-decision-engine-spec-v0.1.md`
§21A. The deferred "transaction recording vs. Playbook recommendation"
question from B.5.2B remains open and is not addressed by this
resolution — whether the middle band (exceeds `maximumNormalTrim` but
HC-003-clean) should ever surface a UI signal remains a possible future
execution/UX consideration, not decided here.
