## 2. Threshold math

```
PositionSizingState (target-position.ts):
  UNDERWEIGHT   if weight < 40
  WITHIN_TARGET  if 40 <= weight <= 45      // inclusive at both ends
  OVERWEIGHT     if weight > 45

ConcentrationState (concentration.ts):
  WITHIN_TARGET if weight <= 45             // same inclusive upper bound
  MODERATELY_OVERWEIGHT if 45 < weight <= 51.75

HC-001: triggered = weight > 50 — all three test weights (44.9-45.1) are far below this, so already cleared

ADD action zone:
  accumulationEnabled + WITHIN_TARGET        -> ACTIVE
  accumulationEnabled + MODERATELY_OVERWEIGHT -> WATCH
```

Both models (`ConcentrationState` and `PositionSizingState`) use the identical inclusive-at-45% rule, so they transition together at this boundary — unlike the HC-001 case, there is no split-second disagreement between the two classifications here.

## 5. Key question — what happens to capacity/stance/zones at 45.0%/44.9%? (do not assume HOLD is automatically "done")

**Stance stays `HOLD` at all three weights — but not because "HOLD is automatically correct."** At 45.1% (MODERATELY_OVERWEIGHT), `HOLD` is what the current code returns for that concentration tier — a case that the roadmap already flags as a design question (see §6). At 45.0%/44.9% (WITHIN_TARGET), `HOLD` comes from a *different, intentional* code path — `stance-rules.ts`'s explicit WITHIN_TARGET fallback, commented `// Phase C will refine with valuation/fundamentals signals` — this is the documented placeholder behavior, not a mismatch.

**Action zones show a real, meaningful transition:** ADD moves from `WATCH` (45.1%) to **`ACTIVE`** (45.0%/44.9%) — a full clearance to the "can add" zone, not merely a lesser-restricted state. This is the most significant behavioral change across this boundary.

**Trim/add capacity do NOT drop to zero across the board at WITHIN_TARGET** — this is the most important nuance surfaced by this stage. With `shares` pinned at 692 (`weightShareRange.max`):
- `trimCapacity.minimum` = 0 at all three weights (weight-only view: no *mandatory* trim needed once shares are at/below the weight ceiling).
- `trimCapacity.preferred` = 42 and `trimCapacity.maximumNormal` = 76 at **all three weights, including both WITHIN_TARGET cases.**

This is because `preferred`/`maximumNormal` are computed from the **Feasible Strategy Range** (core-aware, `[616, 650]`), which is *tighter* than the weight-only range (`[616, 692]`) — the core ceiling (650) binds before the weight ceiling (692) does. So a position can be `WITHIN_TARGET` by weight and still show non-zero "headroom" toward the core. **This is intentional, documented model behavior** (Minimum is weight-only; Preferred/MaximumNormal are core-aware), not a bug — but it does mean "WITHIN_TARGET" must not be read as "zero capacity in every tier."

## 6. Rule / model design question (pre-existing, reconfirmed only at 45.1%)

Only the 45.1% scenario lands in `MODERATELY_OVERWEIGHT`, reconfirming the same already-tracked gap from B.5.3A: current code returns `HOLD` there, while spec §18 groups `MODERATELY_OVERWEIGHT`/`OVERWEIGHT` together under `HOLD_TRIM`. **Not fixed, not re-classified** — same status as before. The 45.0%/44.9% (`WITHIN_TARGET`) scenarios do **not** exhibit this gap; their `HOLD` is the intentional Phase-C-pending default, not a mismatch.
