### Constraints
- **INPUT:** weight 58.6%, `shortTermMaxWeightPct` 50%, thesis INTACT.
- **CALCULATION / RULE:** `checkHC001` — 58.6% > 50% → triggered. `checkHC002` — thesis ≠ BROKEN → not triggered.
- **OUTPUT:** `constraints.fired = [HC-001]`, `constraints.accumulationEnabled = false`.
- **PASS.** HC-003 not exercised (no transaction in this stage — by design, it is invoked only by `AddTransactionModal`, not `runDecisionEngine`).

### Stance
- **INPUT:** `concentration.state = SEVERELY_OVERWEIGHT`, `thesis.health = INTACT`.
- **CALCULATION / RULE:** `deriveStance` (`src/domain/playbook/stance-rules.ts`) priority matrix — not BROKEN, not WEAKENING → `SEVERELY_OVERWEIGHT → HOLD_GRADUALLY_TRIM`.
- **OUTPUT:** `stance = "HOLD_GRADUALLY_TRIM"`.
- **PASS** — matches spec §18 and the §33 worked example exactly.

### Action Zones
- **INPUT:** `concentration.state = SEVERELY_OVERWEIGHT`, `accumulationEnabled = false`.
- **CALCULATION / RULE:** `deriveActionZoneState` (`src/domain/playbook/action-zones.ts`) per zone type.
- **OUTPUT:** ADD `INACTIVE`, HOLD `ACTIVE`, TRIM_1 `ACTIVE`, TRIM_2 `WATCH`, THESIS_REVIEW `CONDITIONAL`.
- **PASS** — ADD correctly blocked (accumulation disabled AND not WITHIN_TARGET, consistent with spec §22's ADD-eligibility rule); TRIM_1 active is correct for a severely overweight position.

### Scorecard
- **INPUT:** static `unityScorecard` seed + computed concentration state/weight.
- **CALCULATION / RULE:** `calcPositionFitScore` — `100 − 200 × ((58.6−45)/45) = 39.56/100 → round(3.956) → 4/10`, state "Neutral" (≥4). `calcConcentrationRiskScore` — SEVERELY_OVERWEIGHT → mapped 2/10 "Elevated". `fundamentals`/`valuation`/`momentum` — pass-through of seed via `deriveSignals`.
- **OUTPUT:** `positionFit = {4, Neutral}`, `concentrationRisk = {2, Elevated}`, `fundamentals = {8, Positive}`, `valuation = {5, Neutral}`, `momentum = {7, Positive}`.
- **PASS** for `positionFit`/`concentrationRisk` (real, computed; matches spec §9's worked formula ≈39.6/100 exactly). **NOT YET IMPLEMENTED** for `fundamentals`/`valuation`/`momentum` (static pass-through, Phase C scope — not scored as a failure per the B.5 roadmap's explicit instruction).

### Trim Sizing
- **INPUT:** `tacticalInventory.aboveCoreMax = 252` (902−650), `sharesToTarget = 210` (902−692, where `targetShares = floor(62,280 × 0.45 / 40.46) = 692`).
- **CALCULATION / RULE:** `calcTrimSizing` (`src/domain/portfolio/concentration.ts`) is called with `tacticalInventory.aboveCoreMax` (252) directly as `maxTacticalTrim`. **Spec §21 defines `max_tactical_trim = min(shares_to_target, available_tactical) = min(210, 252) = 210`** — the code never takes this `min`.
- **OUTPUT:** `trimSizing = { level1: 76, level2: 88, level3: 88, maxTacticalTrim: 252 }`. Spec-correct values would be `min` base 210 → level1 ≈ round(210×0.30)=63, level2 ≈ round(210×0.35)=74, level3 ≈ 73.
- **FAIL — IMPLEMENTATION BUG.** The engine stages 252 tactical shares for potential trimming, but only 210 shares are needed to reach the 45% target. This is a concrete formula omission (the `min()` step from spec §21 §21 is simply missing from `calcTrimSizing`'s call site in `engine.ts`), present since the original Phase A/B implementation (predates all B.5 and pre-B.5 sessions), never previously caught. **Not fixed** — flagged only, per instruction not to change rules to make validation pass.

## 7. Implementation bugs

1. **Trim sizing omits the `min(sharesToTarget, availableTactical)` step from spec §21.** `src/domain/engine.ts` calls `calcTrimSizing(tacticalInventory.aboveCoreMax)` — it should call `calcTrimSizing(Math.min(sharesToTarget, tacticalInventory.aboveCoreMax))`. Effect on Unity baseline: stages 252 shares instead of the spec-correct 210 (42-share overstatement, ~20% too much). Not fixed in this validation pass.
