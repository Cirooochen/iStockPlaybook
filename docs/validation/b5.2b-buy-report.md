## 1. Pre-BUY state

## 2. Exact BUY input

`applyBuy(unitySeed.position, { shares: 50, priceEur: 40.46 }, currentPriceEur: 40.46, oldTotalPortfolioEur: 62280)` — bought at the current market price, funded from existing portfolio cash per the approved convention. Price, thesis, fundamentals, valuation, and momentum held constant.

## 3. Post-BUY accounting

| Field | Value | Formula |
|---|---|---|
| Shares | 952 | 902 + 50 |
| Average cost | **€28.43** | (902×27.76 + 50×40.46) / 952 |
| Position value | €38,517.92 | 952 × €40.46 |
| Unrealized return | **42.33%** (down from 45.75%) | (40.46 − 28.43) / 28.43 |
| Realized P&L | none — BUY never realizes gains/losses | `applyBuy` has no realized-gain output at all (only `SellResult` does) |

**Why average cost rose and unrealized return fell, even though price didn't move:** the BUY price (€40.46) is *above* the pre-existing average cost (€27.76). Blending 50 new shares in at that higher price pulls the weighted-average cost up (27.76 → 28.43) — standard weighted-average dilution, not tax-lot accounting (spec §3). Since unrealized return is measured against the *new, higher* average cost, the % return compresses (45.75% → 42.33%) even though the original shares' absolute euro gain is untouched and the market price is unchanged. This is expected, correct accounting behavior, not a bug.

## 5. Concentration transition

Exact threshold math: ratio = 61.85 / 45 = 1.374. Severe-overweight boundary = 45 × 1.30 = 58.5. **61.85% > 58.5% → SEVERELY_OVERWEIGHT.** The position was *already* above this boundary pre-BUY (58.6% > 58.5%), so **no tier transition occurs** — concentration numerically worsens (58.6% → 61.85%) but stays within the same, most-severe classification bucket. This is the mirror image of B.5.2A, where the SELL crossed a tier boundary; this BUY does not cross one because it starts and ends in the same (worst) tier.

## 7. Hard constraints — accounting vs. rules-layer distinction

**A. Can the accounting engine process this BUY mathematically?** Yes, cleanly — `applyBuy` computed shares, blended average cost, position value, and weight correctly (§3–§5), with no errors or edge cases.

**B. Does the strategy/rules layer say this BUY should be permitted?** **No.** `HC-001` was already triggered *before* this transaction (58.6% > 50% short-term ceiling) and remains triggered after (61.85% > 50%) — `accumulationEnabled` was `false` both before and after. Per spec §16/§22, accumulation should not be occurring at all while this hard constraint is active.

**These are separate questions, not conflated:** the engine has no trouble computing the result of this transaction; whether the *transaction itself should have been allowed to occur* is a different matter, and the current answer is **it does occur anyway** — see the design question below.

`HC-002`: not triggered (thesis not BROKEN, unchanged). `HC-003`: **not applicable to BUY at all** — it exists specifically to protect against a SELL breaching the core minimum; a BUY can't breach a floor by adding shares. Confirmed in code: `AddTransactionModal.tsx` only computes `hc003` when `type === "SELL"`; for this BUY it is always `null`.

### Design question surfaced (not a bug)

**`AddTransactionModal`'s Confirm button has no gate tied to HC-001 at all.** Its `canConfirm` logic is `isValid && !hc003?.triggered` — `isValid` only checks `price > 0 && shares > 0 && !oversell`. There is nothing in the UI that consults `accumulationEnabled` or HC-001 for a BUY. In this scenario, a user could freely record this 50-share BUY even though the Playbook's own rules say accumulation should be disabled — and the engine will happily compute new (worse) numbers for it.

This surfaces a genuine, previously-undocumented product question:

> Should a BUY be blocked at transaction-entry time when HC-001 is active (mirroring how HC-003 already blocks a core-breaching SELL) — or is unrestricted transaction recording intentional, since the app may need to record a real-world transaction that occurred even though the Playbook would not have recommended it?

**Classified as RULE / PRODUCT DESIGN QUESTION, not an implementation bug.** No blocking behavior was changed in this validation pass, per instruction.
